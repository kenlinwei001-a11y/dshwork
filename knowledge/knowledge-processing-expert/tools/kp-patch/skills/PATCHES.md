**插入片段**：

```markdown
<!-- kp-patch:v1 -->
## 工序之外的三道机制（v1 新增）

七道工序解决「怎么处理」；下面三道解决「**怎么知道没漏**」。它们不是工序，是门禁。

| 机制 | 模块 | 作用 | 判据 |
|------|------|------|------|
| **源侧索引 source ledger** | `corpus_pipeline/source_ledger.py` | 让「漏了什么」成为可计算的问题 | 引用/表/带单位数值/标题/题注/设备参数 逐类枚举 |
| **闭环校验 closure verify** | `corpus_pipeline/closure_verify.py` | `S − P − 豁免 = ∅` | C1 依据 / C2 关键取值 / C3 章节 / C4 设备参数 / C5 题注 / C6 装配 / C7 关系 |
| **分步门禁 stage gates** | `corpus_pipeline/stage_gates.py` | 每步一道闭环，落在**可重做单元的出口** | S0–S11；含**探针正样本标定** |

**为什么必须有**：旧 `validate_extraction` 的三个循环都是 `for x in ext.get(...)`——
**只遍历产物**。对产物集合的任何遍历，逻辑上不可能发现「属于源而不属于产物」的元素。
因此「依据漏抽 54 条」这类缺陷会**静默通过**，不是校验不够严，是方向错了。

**契约扩展（30 → 32 文件）**：

| 新增文件 | 用途 |
|----------|------|
| `chunks/sentences.jsonl` | 句子层：Claim 追踪的最小单位，稳定 ID 可回溯到 chunk |
| `source_ledger.json` | 源侧索引：闭环校验的基准 |

**判定权归属**：门禁由**编排器**调用，**不由抽取/写作 Agent 自判**。
探针未过标定 ⇒ 该项 `invalid`，**不得输出「无误」**。

**可替换环节**：实体/关系/推理/图存储四个环节走 `corpus_pipeline/providers.py` 的 provider 接缝；
换实现（例如换成外部图基础设施）**不需要改任何门禁判据**。缺能力时该项判 `invalid`。
```

## 2. `knowledge-processing-toolchain`

**锚点**：文件末尾（追加）

**插入片段**：

```markdown
<!-- kp-patch:v1 -->
## 客观判据清单（判定不消费 LLM 的意见）

`corpus_pipeline/objective_criteria.py` 提供 12 条**确定性**判据（K1–K12）。
判据类型仅允许 8 种：**集合差 / 守恒等式 / 正则计数 / 数值比较 / 哈希一致 / 图算法 / 枚举成员 / 覆盖率比值**。

**三条铁律**：

1. **LLM 产出候选，工具判定候选是否合格**；判定**不消费 LLM 的意见**。
2. **无法客观化的项不得冒充 pass** —— 标 `judgment_required`，
   既不进自动门禁也不计为通过，交人工。
   当前明确列入的 3 项：论证是否成立、证据支持等级的语义判断、取舍是否可接受。
3. **探针必须自证**：每个探针须先在源中命中一个已知存在的正样本；
   未过标定则该判据 `invalid`。
   （教训：曾三次因探针故障把「探针坏了」误报成「源里没有」。）

**为什么不能用 NLP 分类器替代**：那只是把「LLM 主观」换成「模型主观」，
仍是不确定判定；写进 pass 通道比没有门禁更糟——它给了一个**虚假的保证**。

**需要的是确定性组件，不是模型**：中文分句器、量纲归一表、别名归并（编辑距离）、
表格解析器。四者均为输入确定、输出确定、可单测，且标准库即可实现。
```

## 3. `extraction-quality-audit-skill`

**锚点**：文件末尾

**插入片段**：

```markdown
<!-- kp-patch:v1 -->
## 闭环审计（对「完整性」的审计，而非仅「自洽性」）

本 skill 原有的审计维度（结构完整性、证据覆盖、关系合法性、跨项目污染、孤立节点）
检查的是**产物内部的自洽性**。它们**无法发现遗漏**——因为遗漏的东西不在被遍历的集合里。

补一层**闭环审计**：以源侧索引为基准做集合差。

| 闭环 | 判据 | 阈值 | 失败含义 |
|------|------|------|----------|
| C1 依据 | `原稿《》 − evidence − 豁免 = ∅` | 依据类缺口 = 0 | 报告引用的规范未登记，时效无法核查 |
| C2 关键取值 | `原稿「数字+单位」 − 节点值 − 量纲等价 = ∅` | 缺口 = 0 | 原稿有该数、图谱没建模 |
| C3 章节 | `原稿标题 − outline = ∅` | ≥ 98% | 抽取漏章 |
| C4 设备参数 | `原稿设备参数语句 − 设备节点 ≈ ∅` | ≥ 80% | 明细表无法重建 |
| C5 题注 | `原稿表/图题注 − 成稿 = ∅` | ≥ 60% | 表图未重出 |
| C6 装配 | `defined 且非明细节点 ∩ 成稿引用` | ≥ 95% | 抽到了没写进去 |
| C7 关系 | `应有 claim 关系 − 已有边 = ∅` | 各 100% | 关系词表缺类型 |

**两个必须遵守的细节**：

- **量纲归一**：不归一，「5000 万元」与「50000000 元」会被判成两个不同的数，产生**假缺口**；
  假缺口会磨损门禁可信度（报得太多，人就学会忽略）。
- **探针自证**：未过标定的探针，其判据输出 `invalid`，不得输出「无误」。

**输出契约**：`{id, name, total, covered, exempt, missing[], recall_pct, threshold, verdict}`
，`verdict ∈ {pass, FAIL, invalid}`。**不接受「看起来没问题」这类输出。**
```

## 4. `semantic-graph-compilation-skill`

**锚点**：文件末尾

**插入片段**：

```markdown
<!-- kp-patch:v1 -->
## 论断级关系词表（7 类扩展）

原 `TEN_RELATIONS`（has_value / has_attribute / instance_of / part_of / causes /
depends_on / supports / contradicts / temporal / located_in）覆盖的是**事实与实体**关系。
论断之间还需要 7 类，否则 `premise_refs` / `derived_from` 字段**无从填充**——
不是不想填，是**没有可填的语义槽**。

| 关系 | 语义 | 端 |
|------|------|----|
| `cites` | 这条结论依据哪条规范/文件 | claim → mandate |
| `restates` | 总论/结论复述各章结论 | claim → claim |
| `causes` | 因果链条 | claim → claim |
| `derives` | 显式推演派生 | claim → claim |
| `precedes` | 论证顺序/前置条件 | claim → claim |
| `quantifies` | 结论与其数值绑定 | claim → node |
| `specializes` | 通则落到本项目 | claim → mandate |

实现：`corpus_pipeline/relations_ext.py`（`CLAIM_RELATIONS` + `derive_expected_relations`）。

**「复述层」必须是节点层，不只是边**：可行性研究报告的「总论」与「结论」按体例是
**全篇论断的复述层**。若该层没有 claim 节点，`restates` 边无从建立，
后果是：①改一处漏三处无法被机检；②「结论章不得出现新数」无法机检。
因此编译时须保证总论/结论章**成层**（有 claim 节点），而不只是补边。
```

```markdown
### 返回契约（v1 增补字段）

原契约 4 个字段保留，**增补 1 个必填字段**：

    draft_md:           正文 Markdown；数值一律写 {{node:N-xxxxxxxxxxxx}}（含 node: 前缀）
    node_mentions:      [{node_id, char_span, form}]
    new_claims:         [{text, supports[], evidence[]}]
    unresolved:         [{what, why, need_from_client}]
    unreferenced_nodes: [{node_id, reason}]    # ← 新增，必填

**`unreferenced_nodes.reason` 只能取自固定枚举**（不得自由文本）：

| reason | 含义 |
|--------|------|
| `可省略·明细类` | 设备铭牌参数、财务明细等，按可研深度裁剪 |
| `有意留白·undefined` | 依赖缺失，正文已按 instruction 写定性措辞 |
| `有意并列·冲突项` | 数值冲突，已以「⚠ 待审」并列呈现 |
| `跨章已引` | 在本报告其它章节已引用 |
| `漏引` | **不应出现**；出现即视为装配缺陷 |

**为什么必须填**：门禁 C6/K10 用「defined 且非明细节点 → 成稿引用率 ≥ 95%」判定装配完整性。
没有这张表，机器无法区分「有意省略」与「漏了」——
本项目的实测是 12 个未引用节点中有 3 个是**真漏引**（表格里的数字被散文概括掉了）。
```

## 附：为什么改 skill 而不是改提示词

这五处都不是「不知道该做什么」的问题——「依据要登记」「节点要引用」「结论不得有新数」
都是常识。问题在于：**自然语言指令只能靠自觉执行，而可机检的判据不能在失败时假装通过。**

本次实测的证据：我自己写的 skill 里没有「逐条核销依据清单」这条，
于是我按重要性抽了 67 条依据，剩下 **54 条从视野里消失**，而且**没有任何东西提醒我**。
把规则写得更长不会改变这一点；**让它变成跑不过就是跑不过的检查，才会改变。**
