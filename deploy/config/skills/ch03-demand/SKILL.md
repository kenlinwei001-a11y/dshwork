## 两条硬约束（审核实测踩过的坑，务必遵守）

### ① 不适用项：一句话说完，不许展开

任务书 §3.1 列出了本节「已判不适用的项」及 AP 号。对这些项：

✅ **正确**：本项目不涉及X，理由Y（AP-xxx）。
❌ **禁止**：为它单独立标题、成段论证、或为其编造推演值。

**已发生的错误**：1.2 把「政府资本金注入」（AP-030）与「拟新组建项目法人」（AP-047）
各写成一整节，甚至现编「政府资本金注入金额为0万元（11800-5500-6300=0万元）」——
这个推演值根本不存在。凡含不适用项的章节都会犯同一个病。

### ② 推演只用算式表里有的，口径不可混

`推演算式.yaml` 是唯一权威。表里没有的算式**不许自己列**。

**已发生的错误**：3.2 用 `15600−14600=1000㎡` 得出「超指标」，
但 15600 是总建筑面积（含地下 1800），14600 只是地上用房需求——**口径不可比**，
且与同章「缺口 1280㎡」互斥，一处说超、一处说缺。

**同一事实的多个口径**：必须并列且说明关系（如 480 = 地上未归属面积，解释了
「用房构成缺口 1280」与「地上面积缺口 800」为何差 480），不得只取一个当成结论。

## 推演必须走 Semantica（本章 7 个推演槽位）

**本章推演槽位**：GAP-3.1 科研用房需求面积、研究生等用房需求面积、总需求面积、公共服务配套面积；GAP-3.2 用房构成合计、地上与用房构成差额、设计规模与指标差额

### 铁律：推演不得手算

`280×16=4480` 这种也必须走工具。手算不可复现、不可审计、事后无法回答"这个数怎么来的"。

### 四步操作

```bash
cd "$WORKSPACE"

# ① 健康检查（不确定服务是否在跑时先做）
python3 corpus_pipeline/evo_semantica.py --ping
# 期望：SEMANTICA-OK tools=15

# ② 跑本章推演（自动完成：读算式表 → 调 run_reasoning → 写 trace → 比对结果）
python3 corpus_pipeline/evo_derive.py --sections GAP-3.1

# ③ 校验结果
python3 corpus_pipeline/evo_derive.py --verify
# 期望：DERIVE-VERIFY OK 推演 N｜已推且一致 N｜待核 0｜缺声明 0
```

### 四步分别产出什么

| 步 | 产出 | 落在哪 |
|---|---|---|
| ① | 工具可用性 | 终端输出 `tools=15` |
| ② | 派生事实 `DF-*` | `关联图谱.db::facts` + `pkg_slots.derived_id` |
| ② | 溯源串 `semantica:run_reasoning:DF-*` | `pkg_slots.trace` |
| ② | 算式与结果 | `推演算式.yaml` + `pkg_slots.value_num` |
| ③ | 一致性判定 | 终端输出 `核对=✓/✗` |

### 算式从哪来（不得自己编）

**本章推演的算式必须已在 `推演算式.yaml` 声明**。没声明的会被判「缺声明」而停下：

```bash
# 查本章有哪些算式已声明
grep -A2 "GAP-3.1" 推演算式.yaml
```

若某个推演槽位在表里没有算式 → **停下来报告**，不要自己编一个算式算。补声明的责任人是指挥方，不是写作 agent。

### 三种禁止行为

| 禁止 | 为什么 |
|---|---|
| ❌ 自己拿计算器算 | 无 trace，审核判 P2 复算失败 |
| ❌ 把推演改写成「说明」或「缺口」 | 逃避推演，审核判 P4 缺口未静默填 |
| ❌ Semantica 不可用时直接跳过 | 必须停下来报告 `blocked`，不得降级 |

### 核对不一致怎么办

`核对=✗` 表示「算式算出的值 ≠ 声明的结果」。这时：

1. **不要改正文去迎合**——冲突以工具结果为准
2. 检查 `推演算式.yaml` 里该条的 `result` 是否口径错（百分比缺 ×100、单位换算错）
3. 修 `推演算式.yaml` 后重跑 ②
4. 两侧都合理时并列呈现 + 「本节不裁决」

#

### 正文必须给算式（trace 属工程侧，不必写进正文）

每个推演值在正文里必须给**算式与输入来源**，让读者能人工复算：

```
✅ 年耗电量 13800×55÷1000=759 kW（科研用房 11400 ㎡，55 W/㎡）
❌ 年耗电量 759 kW（只给结果）
```

`semantica:run_reasoning:DF-*` 这类 trace **不必写进正文**——它是工程内部回读机制，
落在 `pkg_slots.trace`（`evo_derive.py` 已自动写入），在交付清单/附录体现即可。
真实合格可研（上财案例）正文 0 trace 仍是合格报告。

## 写完必做：一键收尾（自动触发变更传播）

**每节/每章写完，必须执行这条命令**——它会自动完成「入库 → 比对基线 → 传播分析 → 重拍基线」：

```bash
python3 corpus_pipeline/evo_change_propagate.py --autopilot <节号>
```

### 这条命令做什么

| 步 | 动作 | 为什么 |
|---|---|---|
| ① | `evo_context_db --update <节号>` | 不入库，下游 agent 查不到 |
| ② | 与基线快照比对，抽出变化的 P-id | **任何信息变化都会触发 diff** |
| ③ | 图遍历 + **Semantica 传播推理** | 算出哪些章受影响、哪些口径必须重算 |
| ④ | 下发 `变更待办/待办-第N章.yaml` | 受影响章的 agent 据此做**二次写作** |
| ⑤ | 重拍基线 | 本次状态成为下次比对起点 |

### 传播分析的两条腿（缺一不可）

| 腿 | 手段 | 能发现什么 |
|---|---|---|
| 图遍历 | `typed_edges` 的 uses / depends / derives_from | 「哪些节**曾经引用**过这个值」 |
| **Semantica 推理** | `run_reasoning` + `传播规则.yaml` | 「哪些下游口径**在语义上必须重算**」——包括图里没建边的隐式依赖 |

例：改「总投资」→ Semantica 推理出需重算「单位建筑面积投资、国拨资金占比、学校自筹占比」，
这些口径所在节可能没有 `uses` 边，图遍历抓不到，只有传播规则能覆盖。

### 触发时机（不要漏）

- 本章**初稿写完** → 每节跑一次
- **改了任何数值或表述** → 立刻再跑（这就是二次写作的入口）
- 收到 `变更待办/待办-第N章.yaml` 里有本章条目 → 改完后再跑，确认待办清空


### 触发方式：**人工在前端触发**（不是自动）

| 谁 | 做什么 |
|---|---|
| **你（章节 agent）** | 收到 `变更待办/待办-第N章.yaml` 有条目 → 做**针对性调整** |
| **人工（用户）** | 在前端选节号点「触发变更传播」→ 系统跑 diff → 推送给受影响章 |
| 变更中心 | 执行传播分析并按章下发待办 |

**你不需要自己触发传播**——你只负责：
1. 写完后跑 `--autopilot <节号>` 建立基线（这是下一次 diff 的起点）
2. 收到待办后按 level 针对性调整
3. 改完再跑 `--autopilot` 确认待办清空


### 回改入口：审核待办（与变更待办并列）

审核专家判出 blocker 后会按 `back_to` 分流，属于正文问题的推给你：

```bash
cat 审核待办/待办-第<N>章.yaml
```

每条含：`section`（哪节）｜`blocker_id`｜`dim`（哪个维度没过）｜`where`（第几段）｜`what`（问题）｜`suggestion`（建议改法）

| `back_to` | 推给谁 | 你该做什么 |
|---|---|---|
| `write` | **你** | 按 `what` 改正文；改完重跑 `--autopilot` |
| `extract` | 抽取专家 | 不是你的活——不要改正文去迎合，等抽取侧修完重出包 |

**与变更待办的区别**：
- `变更待办` = 别的节改了、波及到你 → 你被牵连要同步
- `审核待办` = 你自己这节没过审 → 你要改

**改完怎么确认**：重跑 `--autopilot <节号>`，再等审核侧重新判定；待办文件不会自动删，以最新判定为准。

### 如果本章是「二次写作」

先读自己的待办：
```bash
cat 变更待办/待办-第<N>章.yaml
```
按 `level` 处置：
- `SYNC` → **必改**，该值在本节被引用，同步为新值
- `REVIEW` → **送审**，引用该值但口径可能不同，标注待确认后再改
- `CAUSAL` → **因果传播**，Semantica 判定受影响，核对是否需要调整表述

改完再跑 `--autopilot`，待办会被新结果覆盖。

## 各类输入的写法（通用）

本章各输入的**具体条数**见 `写作输入包/第N章-*.yaml` 的 `_counts`，此处只讲怎么写：

| 类别 | 怎么写 | 硬要求 |
|---|---|---|
| 值型 | 客户直接给的数值，原值+单位 | 数值后紧跟〔P-id〕，不换算 |
| 推演 | 由已知值算出 | **必须写出算式及其全部输入**，标「算式派生：a+b=c」 |
| 检索 | 需查标准/政策/规划 | **点名全称+文号**，不得只写「按相关标准」 |

## 本章关键：定建设规模

本章定的面积/投资/工期是**后面第5章工程方案与第7章投资的输入**。
写完必须 `evo_context_db.py --update <节号>` 入库，否则后续章取不到。

## 写法要点

每项按五步写透：**现状与需求 → 依据与口径 → 推导与判断 → 校核与边界 → 措施与影响**。
段数与表格数按任务书 §4 的形参数（案例参照），只借形不借值。

## 硬规则

1. **只写本章**——越界写其他章内容视为违规
2. 数值后紧跟〔P-id〕；算式派生写「算式派生：a+b=c」
3. 不得编造：设备单价、征收补偿、注册资本、信用代码、法人、股东、运营成本
4. 判断不越界：风险等级/等保/高耗能/达标 → 「待有资格主体判定」
5. **冲突默认两侧并列 + 标「本节不裁决」**（不自行选值）。仅当差额已算清、两侧口径已闭合时，改为「暂按 <值>（责任方：…；阶段：…）」，并删去「不裁决」——**未闭合前不得删**
6. 前章结论从数据桥取，不重复推演、不与之矛盾
7. 字数由 `人工卡片/第<n>章.md` 定，不自行预设
