# 溯源写作与反向回读（Provenance Writing & Reverse Readback）

正文不是自由写作，而是把图谱节点**展开**成可读文本，同时保持「每个论断都可反向追溯到
图谱节点与证据」。这是本 skill 与普通写作的本质区别。

## 1. 单源事实（Single Source of Truth）

- 每个 fact **只在一处**完整写出（通常是「事实与现状」章节的事实表）。
- 后文再次引用同一事实时，只写引用（如「见事实 F03」或数值简写），不重复铺陈，
  避免多处抄写导致数字漂移。
- 同一数值在全文只允许出现一个「权威来源」，其余为派生引用。

## 2. 论断级溯源绑定

每句承载论断的正文，末尾用**行内溯源标记**绑定图谱节点：

```
〔CL3｜R5｜E1,E3〕
```

含义：该句对应 claim CL3，推导自 reasoning R5，证据为 E1、E3。
- 原始事实句 → 绑定 `fact id + evidence id`。
- 推演结论句 → 绑定 `claim id + reasoning id + evidence ids`。
- 建议/行动项句 → 绑定 `claim id + evidence ids`（CONTEXT 不判真值）。

溯源标记可折叠为「证据附录」中的完整溯源表，正文用简写引用。

## 3. 冲突的显式呈现

凡涉及 `conflicts` 的论断，正文用「⚠ 待审」框显式呈现：

> **⚠ 待审事项**：〔CF1｜高〕§5 称「材料支持缺口约 5 GWh/月」由 39 GWh/月（流量）减
> 34 GWh（存量）得出，混淆月度需求率与一次性总库存。涉及 F13、F08、R6、CL4。

- 不替用户裁决；列出受影响节点与建议的核实方向。
- 冲突影响下游结论时，下游结论同步标注「受 CFx 影响」。

## 4. 证据性质分层措辞

按 evidence `kind` 选择动词与限定词：

| kind | 措辞示例 |
|------|----------|
| 一手 | "月报显示…"、"确认订单合计…" |
| 预测 | "客户滚动预测…"、"预计…" |
| 承诺·未入库 | "S1 口头追加…，尚未入库，不视为已确认库存" |
| 计划 | "维护计划安排…" |
| 历史 | "历史同类维护平均…" |
| 协议 | "服务水平协议约定…" |

## 5. 反向回读（Reverse Readback）

客户改稿后，须把修改**回读**到图谱，保持正文与图谱一致：

1. 对改动段落逐句定位其溯源标记（或推断其对应的 fact/claim）。
2. 判断改动的语义类别：
   - **改数字/口径** → 更新对应 fact 的 `value`/`unit`，并检查是否触发 conflicts（口径变化）。
   - **改结论** → 更新对应 claim 的 `text`，复查其 `deps`/`evidence` 是否仍支撑。
   - **增删论述** → 新增/删除 claim 节点，补齐或移除 deps/evidence。
   - **改建议** → 更新 CONTEXT 类 claim。
3. 回读后重新做**前向推演**与**冲突检查**，标记被改动「传染」的下游结论。
4. 不得在回读中丢弃原有溯源链；无法定位来源的改动须显式标注「未溯源」，而非假装绑定。

## 6. 数字一致性核对（写作时查数）

每写一节，调用 MCP 工具 `check_number_consistency(draft_md, facts)` 做确定性查数（零 LLM，
kp-assembly MCP 提供）：

- **bound / unbound**：正文每个数字与事实源（facts）比对；`unbound` 的数字带上下文，是
  「前后不一致」或笔误的信号，须人工核实。
- **inconsistent**：同一 subject 在正文多处出现不同数值（前后不一致），一律「待审」。
- **caliber_issues**：同一 subject 的数值单位不一致（如 `GWh/月` vs `GWh`，流量 vs 存量），
  即口径混淆，一律「待审」。

规则：

- 出现 `unbound` 数字，回到单源事实核对：笔误则修正；派生值则改写为 node 引用并标注派生式。
- 出现 `caliber_issues`，不得把流量与存量直接相减，须统一口径或标注「待审」。
- 交付前再跑一次全篇核对，确保正文数字与图谱 fact 的 `value` 一一对应。
- 与 `detect_numeric_conflicts`（数据源内部冲突）区分：本工具是「正文 vs 数据源」的写作期核实。


## V2.8 新增：部分可核的溯源写法

`range_known` 只有 true/false，但实际有第三态：**部分参数可核、部分不可核**。

### 判据

```json
{
  "range_known": false,
  "status": "部分可核",
  "verified_parts": {
    "mu_z": "✅ 可核（表8.2.1 B类 49m 插值 ≈1.61）",
    "w0":   "✅ 可核（表E.5 上海 R=50 = 0.55）",
    "mu_s": "⚠️ 无法核（表8.3.1 为图片未转录）"
  }
}
```

### 写作要求：拆开写

```
❌ 「风荷载体型系数取 1.3，符合 GB50009 要求」
   —— 一句话把三个参数都当成核过了

✅ 「风荷载体型系数取 1.3（迎风 0.8 + 背风 0.5），属封闭式矩形平面建筑常规取值；
   风压高度变化系数按 GB50009 表8.2.1 B 类地面粗糙度、49m 高度取 1.61；
   基本风压按表E.5 上海市 50 年一遇取 0.55 kN/㎡；
   **体型系数表8.3.1 原文为图示，逐项核对待补。**」
```

### 为什么要拆

| 写法 | 读者能得到什么 |
|---|---|
| 「符合规范」 | 什么也得不到，且可能是错的 |
| 「三个参数分别取 X/Y/Z，其中两个已按表核过，第三个待补」 | **能复算、能判断风险在哪** |

### 与其他状态的区别

| 状态 | 写作句式 |
|---|---|
| `range_known=true` | 「满足 XX 规范 X.X 条要求」 |
| `range_known=false`（一般） | 「依据 XX，限值待核」 |
| `range_known=false` + `status=部分可核` | **逐个参数说明核没核** |

### 铁律

> **「部分可核」不能简化成「待核」，也不能简化成「符合」。**
>
> 简化成「待核」丢掉了已核的信息；简化成「符合」把没核的说成核了。
