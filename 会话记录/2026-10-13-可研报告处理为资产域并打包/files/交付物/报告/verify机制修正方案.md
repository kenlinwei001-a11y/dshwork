# verify 机制修正方案（闭环校验）

> 结论先说：**是机制的问题，而且是结构性缺陷**——不是「校验不够严格」，而是**校验的数学对象选错了**。

---

## 一、旧机制的结构缺陷（为什么它必然查不出遗漏）

现有校验函数 `validate_extraction(ext)` 的实现是：

```python
for f in ext.get("facts", []):        # 遍历【产物】
    if not f.get("subject") or not f.get("value"):
        errors.append(...)
for cl in ext.get("claims", []):       # 遍历【产物】
for r in ext.get("relations", []):     # 遍历【产物】
```

**三个循环，遍历的都是产物。** 这带来一个逻辑上的不可能：

> 对产物集合 P 的任何遍历，都无法发现「不属于 P 但属于源 S」的元素。因为那个元素**不在被遍历的集合里**，循环根本不会碰到它。

所以旧机制能保证的是「抽出来的东西**格式对、值合法**」，**永远不可能保证「该抽的都抽了」**——哪怕我把校验写到极致，54 条未登记的依据依旧会一条不漏地穿过去。

| | 旧机制 | 结论 |
|---|---|---|
| 校验对象 | 产物内部（facts/claims/relations 的字段与枚举） | 自洽性 |
| 能否发现遗漏 | **不能（逻辑上不可能）** | ❌ |
| 对「漏抽」的表现 | 静默通过 | 最危险的一类失败 |

## 二、修正后的机制：闭环校验（closure verification）

```
旧：  P ──► 遍历 P ──► 自洽？           （产物内省，看不见 S−P）

新：  S ──► 源侧索引 ledger（独立方法生成）
      P ──► 产物集合
      missing = S − P − 显式豁免        （集合差，漏了就非空）
      missing ≠ ∅ ⇒ FAIL
```

**关键在第一步：把源变成可枚举的索引（ledger）。** 源不可枚举时，「漏了什么」这个问题无法被提出，更无法被回答。

### 2.1 源侧索引（用与 LLM 无关的方法生成）

| 索引 | 生成方法 | 条数 |
|------|----------|------|
| `citations` | 正则扫原稿 `《…》` | 155 个唯一（190 处） |
| `tables` | 数原稿 ```` ```table ```` 块（由 docx 的 w:tbl 决定） | 31 |
| `valued_numbers` | 正则扫「数字＋单位」 | 143 个唯一 |
| `headings` | 正则扫标题层级 | 151 |
| `device_params` | 正则扫 `Q=`/`H=`/风量/全压/静压/功率 | 32 条语句 |
| `captions` | 正则扫 `表N-M`/`图N-M` | 42 个 |
| `images_in_docx` | 读 docx 的 `word/media/` | 12 |

**为什么必须是独立方法**：如果 ledger 也用「读一遍原稿、凭理解记下来」的方式生成，它会继承**同一双眼睛的同一盲区**，S−P 依旧为空。正则/XML 与 LLM 阅读是两条独立通道，差集才有意义。

### 2.2 探针自证（本次最痛的教训）

我这次诊断**三次误判**：把「功率因数」（节能章灯具要求）当成变压器匹配口径、把「需要系数」（节能章表7-2 列标题）当成负荷估算口径、以及正则 `^## 6.5 强电设计` 没匹配到（原稿正文标题不带编号）导致探针区间为空。

**根因：探针没有正样本标定。** 一个探针分不清「源里没有」和「我的正则写错了」，却会输出「源里没有」——这是把探针故障伪装成事实结论。

修正：每个探针必须先在源中命中**一个已知存在的正样本**，命中失败则探针作废、不得出结论。

| 探针 | 正样本（必须命中） | 结果 |
|------|--------------------|------|
| `citations` | 普通高等学校建筑规划面积指标、建筑设计防火规范 | ✅ 有效（命中 190 处） |
| `headings` | 总论、投资估算及资金筹措 | ✅ 有效（命中 151 处） |
| `valued_numbers` | 18319、13032 | ✅ 有效（命中 314 处） |
| `device_params` | 风量 | ✅ 有效（命中 38 处） |
| `captions` | 表1-2、表5-5 | ✅ 有效（命中 48 处） |

**本次探针标定结果：5/5 有效**，全部有效。

## 四、修正前后的行为差异（用本次的真实数据）

| 事项 | 旧机制 | 新机制 |
|------|--------|--------|
| 54 条依据未登记 | 静默通过（校验只遍历抽到的 67 条） | **C1 FAIL**，输出 54 条清单 |
| 29 条设备参数未抽 | 静默通过 | **C5 FAIL**，输出缺抽条数 |
| 原稿 31 张表 / 30 个题注 | 静默通过 | **C6 判定**，输出未重出表题 |
| 3 个节点未引用（双证硕士 5631 等） | 静默通过 | **C7 FAIL**，逐节点点名 |
| 原稿 12 张内嵌图 | 静默通过 | **C8** 图片闭环（本轮先只登记数） |
| 探针自身故障 | 伪装成事实结论（我误判 3 次） | **探针标定**，未过标定即作废 |

## 五、落到哪里（三处小改动）

| 改动 | 位置 | 形式 |
|------|------|------|
| 建 `source_ledger.json` | `corpus_pipeline` 新工序（解析后、抽取前） | 确定性函数 `build_source_ledger(docx/md)` |
| 七道闭环校验 | `corpus_pipeline` 新增 `closure_verify()` | 返回 `{closures:[{id,total,covered,exempt,missing,verdict}]}` |
| 接入门禁 | `quality_gates` / `gate_check` | **missing 非空 ⇒ 该项 FAIL**，由编排器判定 |
| 探针标定 | 上两者的前置 | 未过标定的探针 → 该项 `invalid`，输出「不作结论」而非「无误」 |

**与旧机制的关系**：不替换，是**补一层**——

```
旧 validate_extraction  →  保证「抽出来的对不对」   （保留）
新 closure_verify       →  保证「该抽的都抽了没有」 （新增）
两者都过 → 才允许进入图谱编译
```

## 六、一句话

| 问题 | 答案 |
|------|------|
| 是 verify 机制的问题吗？ | **是，而且是根因**：旧机制遍历产物，逻辑上不可能发现遗漏 |
| 是校验不够严吗？ | **不是**。再严的自洽性校验也查不出缺失——**方向错了** |
| 修正的关键是什么？ | **把源变成可枚举的索引，然后做集合差**；并让探针先自证 |
| 为什么这次能查出来？ | 因为我（被要求反思后）临时写了正则版源索引——**这正是应该固化成机制的东西** |

> 最后一句自省：本次七个闭环全部是我**事后手写脚本**跑出来的。旧机制里没有它们，所以**在你不问的情况下，这 54 条依据、29 条设备参数、3 个未引用节点会安静地留在交付物里**。这不是我不小心，这是机制允许的默认结果。
