# 质量门控需要什么工具（必需 / 有用 / 禁用）

> 问题：verify 是否需要专门的 Python 或 NLP 工具才能实现质量门控？
> 答：**门控本身不需要 NLP**——它需要的是「索引 + 集合运算 + 数值比较」，我已用标准库实现 36 道判据。但有 **4 类确定性组件**会实质提升门控能力，其中 3 类已在本次实现。

---

## 一、结论：门控的逻辑构件与 NLP 无关

已经实现的 36 道判据（12 闭环 + 12 分步门禁 + 12 客观判据），**全部只用标准库**：

| 判据类型 | 用到的能力 | 是否需 NLP |
|----------|-----------|-----------|
| 集合差（引用/题注/节点闭环） | `set` 运算 | ❌ 不需要 |
| 守恒等式（解析/切块/分句） | 计数、字符统计 | ❌ |
| 正则计数（占位符形、手打数字） | `re` | ❌ |
| 数值比较（派生闭合、阈值穿越） | 浮点比较 + 容差 | ❌ |
| 哈希一致（溯源、可复现） | `hashlib` | ❌ |
| 图算法（端点可寻址、无环） | `dict`/`set` 遍历 | ❌ |
| 枚举成员（值域合法） | 集合包含 | ❌ |
| 覆盖率比值（召回率门禁） | 除法 | ❌ |

**原因**：门控问的是「**该在的东西在不在**」，这是集合问题，不是语义问题。语义问题（「这句话什么意思」）才需要 NLP——而它不属于门控。

---

## 二、但确实需要 4 类「确定性组件」

| # | 组件 | 为什么需要 | 是否 NLP | 本次是否已实现 |
|---|------|-----------|----------|----------------|
| ① | **中文分句器** | S2 分句闭环此前**无产物**，门禁无法执行；句子是 Claim 追踪的最小单位 | ❌ 规则引擎 | ✅ `gt29`（见下） |
| ② | **量纲归一表** | 消除「万元 vs 元」「万kW·h vs kWh」造成的**假缺口** | ❌ 领域词表 | ✅ `gt29` |
| ③ | **同义/别名归并** | 实体层要收敛（「上财」vs「上海财经大学」）；用编辑距离即可，无需模型 | ❌ 字符串算法 | ✅ `gt29`（difflib） |
| ④ | **表格解析器** | docx 的 `w:tbl` → 结构化表格（合并单元格/嵌套表） | ❌ 需 XML 解析 | ✅ `s0_docx2md.py`（zipfile+ElementTree） |

> 这四类都不是「模型」，而是**确定性组件**：输入确定、输出确定、可单测。它们的位置在**处理层**（生成索引与结构化产物），不在判定层。

---

## 三、本次实测：三项组件的效果

### 3.1 中文分句器（关闭 S2）

| 项 | 值 |
|----|----|
| 输入 chunk 数 | 1178 |
| 切出句子数 | **1923** |
| 平均句长 | 33.9 字符 |
| 最短/最长句 | 2 / 237 字符 |
| 产出 | `chunks/sentences.jsonl`（稳定 ID = chunk_id + 序号，可回溯） |

**分句闭环随之可判**：`Σ sentence 字符 = Σ chunk 字符`（去空白后应相等或差异可解释）。
实测：Σsentence 61588 vs Σchunk 61602，差 14（标点收尾合并所致，可解释）。

### 3.2 量纲归一表（消除假缺口）

用归一表复检缺口清单：**假缺口 0 处、真实缺口 36 处**。

**本项目的结论**：归一表**未消除任何缺口**——`K4` 报出的 23 条**全部是真实缺口**（原稿含该关键数值，但图谱未建模）。

真实缺口（前 12 条）：

- 0.05 m
- 0.11 米
- 0.15 m
- 0.28 m
- 0.35 %
- 0.35 m
- 0.80 m
- 0.90 m
- 1.10 m
- 1.40 m
- 1.50 m
- 1.7 %

> **归一表的价值在于「防止未来的假缺口」**：有了它，「5000 万元」与「50000000 元」不会被判成两个不同的数。本项目的实测结果是 **0 处假缺口**，说明现有门禁在这一点上没有误报——这也修正了我上一版的一个算式错误（曾把「精确命中」误计为假缺口，报出 36 处）。

**意义**：没有归一表，门控会把「5000 万元」和「50000000 元」判成两个不同的数，产生假缺口；**假缺口会磨损门禁的可信度**——报得太多，人就学会忽略。

### 3.3 别名归并（difflib，非 LLM）

实体名 555 个，归并后 **554 组**，其中多成员组 **1 组**：

- **上海财经大学统计与管理学院** ← 统计与管理学院

## 四、有三类**不能**交给任何工具（含 NLP 分类器）

| 项 | 为什么不能用工具 | 正确处置 |
|----|------------------|----------|
| **论证是否成立** | 用 NLP 打分仍是不确定判定，只是把「LLM 主观」换成「模型主观」 | 拆成可客观化的代理（warrant 非占位率、grounds 可追溯率），**结论标 `judgment_required`** |
| **证据支持等级** | SUPPORT / PARTIAL / CONTRADICT 是语义判断 | 保留 LLM 判断但**标为候选**，不进 pass |
| **取舍是否可接受** | 业务判断，须客户/编制单位确认 | 门禁只报保留率，**不代替结论** |

**这三类的共同风险**：一旦让工具（或 LLM）输出「通过」，就等于用另一种不确定性冒充客观——比没有门禁更糟，因为它给了一个虚假的保证。

## 五、工具清单（可直接落地）

| 优先级 | 工具 | 实现方式 | 现状 |
|--------|------|----------|------|
| P0 | 源侧索引（ledger） | 正则 + XML | ✅ `opt25.py` |
| P0 | 集合差校验器 | `set` | ✅ `opt25/26/27` |
| P0 | 分句器 | 规则引擎（成对符号保护） | ✅ `gt29.py` |
| P0 | 量纲归一表 | 领域词表 | ✅ `gt29.py` |
| P1 | 表格解析器 | zipfile + ElementTree | ✅ `s0_docx2md.py` |
| P1 | 别名归并 | difflib | ✅ `gt29.py` |
| P2 | 向量检索（同义召回） | **可选**：仅用于「找到了吗」的召回，不用于判定 | 未引入 |
| — | LLM 语义判定 | 仅产出候选 | 已有，**不参与 pass** |

**P2 的取舍**：向量检索能提升「遗漏召回」的直觉，但它本身不确定，且**门控要的是精确判定而非相似召回**。因此建议：向量检索只用于**提示可能遗漏**（生成候选清单交人复核），**不写入任何 verdict**。

## 六、一句话

| 问题 | 答案 |
|------|------|
| 门控需要 NLP 吗？ | **不需要**。门控是集合/计数/数值问题，逻辑构件与 NLP 无关 |
| 需要专门的 Python 工具吗？ | **需要 4 类确定性组件**（分句器、量纲归一、别名归并、表格解析），**标准库即可**，无需第三方模型 |
| 向量检索要引入吗？ | **仅作召回提示，不参与判定**。判定必须精确，相似召回不能进 verdict |
| 什么不能用工具？ | 论证成立性、证据支持等级、取舍可接受性——**必须人判，且不得冒充 pass** |
