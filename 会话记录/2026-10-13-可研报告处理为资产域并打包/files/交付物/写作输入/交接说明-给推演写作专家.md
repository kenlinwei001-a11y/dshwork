# 交接说明：让「推演写作专家」写出报告

> 照着做即可。**结论先说**：不要只把三个 MD 和 ZIP 丢给它——那个专家按「注入 / 工具 / 每节工作包」三通道消费，ZIP 里的**语料包目录**才是它真正要读的对象。

---

## 0. 一句话流程

```
解压 ZIP  →  起两个 MCP 服务（每次调用传 corpus_dir=解压后的语料包路径）
          →  给写作 Agent 注入三个小文件（约 27K tokens）
          →  逐节推工作包 project/work_packages/<节>.json，收 draft_md
          →  编排器跑 gate_check_draft，不过则重写
```

---

| 目标 | 需要的输入 | 本包是否够 |
|------|-----------|-----------|
| **A. 还原本报告**（本项目、同事实，重写一版） | 本包全部（含本项目事实 358 条） | ✅ 开箱可用 |
| **B. 写一个新项目的报告**（借形不借值） | 本包 + **新项目的输入事实** | ⚠️ 需你另填新事实，见 §7 |

下面 §2–§6 两种都适用；差别在「facts 从哪来」。

## 3. 起 MCP 工具（这条决定你能不能真用上它的推演能力）

那个专家的 `SKILL.md` 定义它调用 `corpus_get_skeleton / corpus_get_chunk / graph_query / graph_explain / graph_why / evidence_get` 等函数。这些是知识处理工具层的 MCP 服务，**每个调用都要带 `corpus_dir`**，指向上面的 `$CORPUS`。

```bash
KP=/Users/apple/Desktop/workdsh/knowledge/knowledge-processing-expert
"$KP/.venv/bin/python" "$KP/mcp/server.py" --group processing   # 含 corpus_* / graph_* / evidence_get / gate_check
"$KP/.venv/bin/python" "$KP/mcp/server.py" --group assembly     # 含 build_work_package / gate_check_draft / wp_get_facts
```

把这两个 server 注册为 MCP 连接（stdio），每次工具调用的参数形如：

```json
{"corpus_dir": "/Users/apple/workdsh/.test-runtime/preview/workdsh-projects/1667349c74609b4500654ac978662087a947e3f197112fe62706d819b8d081f0/SHUFE-BDC-2019-001", "section": "13-投资估算及资金筹措"}
```

> 若你的环境里没有 MCP 通道，退到 §6 的「路线 B」——用 MD 上下文写，但**推演链解释与闸门会缺失**。

### 4.4 收稿与闸门

每节要求它按返回契约交付：

```
draft_md:      正文 Markdown；数字一律写 {{node:N-xxxxxxxxxxxx}}，不得写字面量
node_mentions: [{node_id, char_span, form}]
new_claims:    [{text, supports[], evidence[]}]
unresolved:    [{what, why, need_from_client}]
```

然后**由编排器**（不是你、也不是写作 Agent）调 `gate_check_draft`。它查三样：

| 检查 | 触发条件 | 处置 |
|------|----------|------|
| **字面数值** | 剥离 `{{node:...}}` 后仍出现数字 | `review`：必须改写为 node 引用 |
| **must_cover 缺项** | 工作包 `outline.must_cover` 的关键词未出现在正文 | `review`：补齐该节内容 |
| **undefined 引用** | 引用了 `status=undefined` 的节点 | `pass_with_notes`：按 `instruction` 写定性措辞并挂 gap |

## 6. 路线 B（降级）：没有 MCP 通道时

把三个注入文件 + **逐章切片**（`写作输入/chapters/NN-*.md`，一次只贴一章）交给它，并明确告诉它「你拿不到工具，推演链与闸门已预先算好，写在切片里」。

相比路线 A 会丢掉三样：`graph_explain` 的推导句、`graph_why` 的冲突决策依据、`gate_check_draft` 的机器闸门。**闸门丢失是主要风险**——你需要在人工环节补做 §4.4 的三项检查。

## 7. 如果要写「新项目」（借形不借值）

本包 358 个节点是本项目的事实，**不得继承**。写新项目时要：

1. 用 `kp-assembly` 的 `instantiate_project(corpus_dir, project_dir, provided_facts, meta)`：
   输入新项目的 `provided_facts`，借用本包的规则/推导链/风格，输出重绑定图库；
2. 新事实**只填源数据**（分类人数、各单位造价、市政接入条件、批复口径），派生量（总建筑面积、总投资、单位造价、综合能耗…）一律由规则算出，不得手填；
3. 缺的新事实按 `推演写作输入包.md` §F 的口径**显式留白**，不估算、不套用本项目；
4. 软约束（规范版本、定额、单方造价）**默认已过期**，须按现行口径重查后再用；
   本包 `external/` 里的条款与判定只对本项目时点成立。

## 8. 八个常见坑

1. **整包塞上下文**：原文 830 KB、骨架 874 KB、graph 整包 220 KB —— 别给。给了它就只会抄。
2. **占位符写错形**：必须是 `{{node:N-xxxxxxxxxxxx}}`（含 `node:` 前缀），写成 `{{节点ID}}` 或 `{{N-xxx}}` 会被 `gate_check_draft` 判为字面数值。
3. **让写作 Agent 自己判卷**：闸门由编排器调 `gate_check_draft`，Agent 的自省不算验收。
4. **先写总论**：总论是全篇投影，先写它必然与后文不一致。
5. **替它裁决冲突**：15 条待审冲突必须并列呈现；取其一或改数会让整章丧失可信度。
6. **用本项目的数值填新项目**：那是借形不借值的红线。
7. **整文件读 chunks.jsonl**：只按 chunk id 取单条。
8. **忽略 `inheritable=never`**：44 个判定量（类别/等级/形式/结论）不跨项目继承，也不得据此作结论性陈述。

## 9. 验收清单（人工复核用）

- [ ] 每节 `gate_check_draft` 的 `verdict` 为 `pass` 或 `pass_with_notes`，无 `review` 未处理项
- [ ] 全文无字面数值（除表号、章号、规范编号）
- [ ] 15 条待审冲突在正文中以「⚠ 待审」并列呈现，未被裁决
- [ ] 15 条缺口处写的是「待 X 确认后生成」类定性措辞，无估算值
- [ ] `warrant` 为空的论断未被补写保证（`CL-必要性-01/02` 等）
- [ ] 3 条不合规项（B-11 已废止规范、B-12 已废止名称、B-14 章节覆盖）已按依据改正或显式标注
- [ ] 2 条待核查项（B-04 喷淋参数表、B-08 附表B）未被下判定
- [ ] 结论章无新数
- [ ] `unresolved` 清单已收集并交回给你
