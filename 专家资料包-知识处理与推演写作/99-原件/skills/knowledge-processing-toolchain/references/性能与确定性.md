## 性能也属"确定性"：四个零 LLM 工具（实测案例）

**分层判据不止管「抽取对不对」，也管「跑得快不快」。**

性能优化是纯确定性工作：计时、判阈值、建索引、缓存 —— **一条 LLM 都不该用**。
把"为什么慢"交给模型分析，等于让它猜；正确做法是**测出来**。

### 案例：七道工序 34 s 里 32 s 在读 YAML

```
实测（corpus_pipeline）:
  yaml.safe_load  nodes.yaml 1.87MB/2410条  36.18 s
  json.loads      同一份数据                0.08 s   → 快 388~797 倍
```

**这不是"感觉慢"，是量出来的。** 四个工具逐个对应一个可量化的瓶颈：

| 工具 | 解决的瓶颈 | 性质 | 实测 |
|---|---|---|---|
| `fastload` | YAML 解析纯 Python 实现慢 | **IO/解析** | 36.18 → 0.08 s |
| `shard_index` | 一次全读不需要的节点 | **索引** | 36.18 → 0.001 s（browse）|
| `bench_perf` | 性能回归无人发现 | **判据** | 阈值超即退出码 1 |
| `caliber_check` | 口径差异被当冲突 | **结构判定** | 3 冲突 → 3 口径差异 |

### 每个工具的分层归属（可对照）

```python
# ① fastload —— 纯 IO
from corpus_pipeline.fastload import load
d = load(Path("graph/nodes.yaml"))        # 无 LLM，纯缓存

# ② shard_index —— 纯索引
from corpus_pipeline.shard_index import build, browse, resolve
build(corpus)                              # 无 LLM，纯分片

# ③ bench_perf —— 纯判据
# python -m corpus_pipeline.bench_perf <dir>   # 无 LLM，纯计时 + 阈值

# ④ caliber_check —— 纯结构判定
from corpus_pipeline.caliber_check import classify_conflict
classify_conflict("土建工程", 6780, 9350, fsm)   # 无 LLM，查表 + 符号判断
```

**四个工具，零 LLM 调用，全部可 CI 回归。**

### 反例：把性能问题交给 LLM 会发生什么

**错误做法**：
```
"我读 nodes.yaml 很慢，你分析一下为什么"
→ 模型回答："可能是文件太大/磁盘慢/内存不足"
→ 无法验证，无法复现，无法回归
```

**正确做法**：
```
计时：yaml.safe_load 36.18 s vs json.loads 0.08 s
→ 瓶颈确定：YAML 解析器
→ 修法确定：加缓存层
→ 回归确定：bench_perf 阈值 0.50 s
```

**判据**：**问题能不能用「计时 + 阈值」表达？能 → 代码，不能 → 才考虑 LLM。**

### 一条新增铁律

> **凡能用「计时 + 阈值」表达的问题，一律走代码；
> 需要「理解为什么」的，才走 LLM。**

**这条与原有的「能确定性计算的不交给模型」是同一个原则**，
只是从「算得对不对」扩展到了「跑得快不快」。

### 阈值不是拍脑袋：必须带变更记录

```python
THRESH_NOTES = {
    "write_41_sections": [
        {"at": "v1.0", "value": 2.0, "why": "按分片理论值 0.136 s × 14.7 拍定"},
        {"at": "v1.1", "value": 3.0, "why": "实测 2.25 s（内部回读 nodes.yaml），2.0 会误报"},
    ],
}
```

**改阈值时必须同时写两件事**：
1. **为什么是这个值**（实测多少、留了多少余量）
2. **优化路径**（不做的话什么时候该收紧）

**只有数字没有理由的阈值，等于没有阈值。**
