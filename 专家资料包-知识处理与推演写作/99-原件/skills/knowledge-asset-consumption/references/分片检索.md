## 分片检索：不依赖章节（可执行契约）

**分片的本质是「按查询的自然边界取数」，章节只是其中一种边界。**
无章节的客户材料同样可以分片 —— 换分片键即可。

### 三种分片键，按文档是否有章节选

| 文档类型 | 首选分片键 | 命令 |
|---|---|---|
| **有章节**（正式报告/规范） | `section` | `kp_cli.py shard resolve <dir> --section 6.7.1` |
| **无章节**（客户材料/散装数据） | **`rule` 依赖闭包** | `kp_cli.py shard closure <dir> --rule R-总投资构成` |
| 两者都可 | `unit` / `label_prefix` / `kind` | `kp_cli.py shard query <dir> --unit 万元` |

### 可执行契约（不是纪律，会 raise）

```python
from corpus_pipeline.shard_index import (
    assert_shardable, NotShardable, resolve_or_full,
    build_inverted, query, resolve_closure,
)

# ① 要分片但不能分 → 必须显式降级，不许静默
try:
    assert_shardable(corpus)
except NotShardable as e:
    nodes = fastload.load(Path(corpus) / "graph" / "nodes.yaml")   # 全读
    log.warning("分片不可用，降级全读: %s", e)

# ② 无章节文档：建倒排 + 按规则取闭包
build_inverted(corpus)                              # 0.6 s 一次性
nodes = resolve_closure(corpus, "R-总投资构成")      # 精确取 4 条上游

# ③ 按值域/名称查
query(corpus, unit="万元")            # 5 条
query(corpus, label_prefix="建")      # 6 条
query(corpus, rule="R-总计算负荷")     # 该规则产出的
```

### 性能基准（可回归，超阈值退出码非 0）

```bash
python -m corpus_pipeline.bench_perf <语料包>
#   browse                0.0013 s / 阈值 0.05  ✓
#   resolve               0.0156 s / 阈值 0.10  ✓
#   write_41_sections     1.1188 s / 阈值 3.00  ✓
#   cache_hit_nodes       0.0661 s / 阈值 0.50  ✓

```

**阈值是实测值 × 3 倍余量。超了就是回归。**

### 实测：三种取数的对比

```
场景：写「投资估算」一章，需要总投资及其全部上游

方案 A  全读 nodes.yaml（长报告场景 41 节）
        36.18 s × 41 = 1483 s（24.7 分钟）

方案 B  一次全读 + 内存
        36.18 s，内存 50 MB+

方案 C  按规则取依赖闭包
        resolve_closure("R-总投资构成") → 4 条，0.0014 s
        41 节合计 0.136 s
```

### 降级必须可见（这是硬要求）

```python
r = resolve_or_full(corpus, section="6.7.1")
assert r["mode"] in ("shard", "full_fallback")
if r["mode"] == "full_fallback":
    # 必须把这个原因写进报告元信息，不许吞掉
    report_meta["data_mode"] = "full_fallback"
    report_meta["reason"] = r["fallback_reason"]
```

**反面教材**：拿无章节的语料包去 `resolve(section=...)`，返回 `[]` 却不报错 ——
调用方以为「这一节没有数据」，实际是「分片键选错了」。
