# 可行性研究报告本体图谱 · 高校科研用房

## 交付物是一份 Word 文档

说在最前面，因为这一点最容易搞反：

| | 是什么 | 交不交付 |
|---|---|---|
| `out/report.docx` | **最终成品**，客户拿到的可研报告 | ✅ 这才是交付物 |
| `out/check.txt` | 一致性检查报告 | ✅ 随文交付，说明查过什么 |
| `audit/` | 派生轨迹与防篡改指纹 | ✅ 备查 |
| `project.yaml` | 实例图，**中间产物** | ❌ 不单独交付 |
| `content.yaml` | 正文模板，**中间产物** | ❌ 不单独交付 |

`project.yaml` 是脚手架，不是产品。只交出一个 YAML 等于交了半成品——**客户要的是能打开、能改、能报审的 Word 文档。**

生成命令在下面「第四步：出稿」。缺 `python-docx` 时先装：`pip install python-docx --break-system-packages`。

## 这个 skill 在解决什么问题

一份可研报告 130 页、十几章、几十张表，但支撑它的事实节点通常只有 60 个左右。其余全是这些事实的自然语言表述，以及它们之间派生关系的解释。

真实样本里，"总建筑面积"这一个数字横跨 7 个专业领域出现 11 次。人工写作时，改一处就要记得改另外十处——记不住，于是出事。我们验过的一份真实报告，第 13 章写 18219，其余十处写 18319。另一份 2024 年的报告，宿舍应建面积声明 485000 ㎡，按它自己写的指标和人数重算是 495750 ㎡。

这些都不是粗心，是人力不可及。**把报告当成图的一次渲染，而不是一篇文章，这类事故在物理上就不可能发生。**

## 五条硬规则

**① 法定基准是发改投资规〔2023〕304号。** 不是任何一份样板报告，也不是客户手上的旧模板。样本可以是错的，法定大纲不能不覆盖。政府投资项目适用《通用大纲》（强制），企业投资项目适用《参考大纲》（参考）。每个垂类必须 `extends` 其中一本。

**② 单一事实源。** 任何事实在图中只存在一份，正文永远是引用而非复制。渲染时注入，不复制粘贴。

**③ 可派生的量不许人工录入。** 总投资是算出来的，不是填出来的。允许手填派生值，等于允许图与正文脱节。

**④ 不得编造。** 没有素材依据、也没有客户答复的量，一律保持 UNKNOWN。不估算、不套用同类项目、不写"暂按经验值"、不用行业均值填坑。凡入图必带 `from`（素材 id + 页码/表号），带不出 `from` 的就不入图——这是这条规则唯一可机检的部分（C8）。禁令清单见 `references/materials.yaml → no_fabrication`。

**⑤ 事实没确认就不写正文。** 宁可空着并说明"待 X 确认后生成"，也不要先写一版占位文字。占位文字会被当成初稿，被润色，然后被遗忘——更要命的是，客户看到通顺的段落就会去改句子，而不是纠正数字。

## 来源路由：每条信息从哪来

这是全 skill 最要紧的一次判断。可研里的每一条信息只可能来自五条路径之一，判定顺序不可颠倒：

| 顺序 | 判定 | 路由 | 含义 |
|---|---|---|---|
| 1 | 能由图中其他节点算出？ | **COMPUTE** | 算。绝不许手填，也不许拿去问客户 |
| 2 | 只存在于客户的组织内部？ | **ASK** | 问，或追素材 |
| 3 | 公开发布、谁都能查到？ | **SEARCH** | agent 自己查，不占客户时间 |
| 4 | 是对已确认事实的组织与表述？ | **WRITE** | agent 起草 |
| 5 | 都不是 | **WITHHOLD** | 留白并写明待补 |

COMPUTE 排第一位是有意的：能算的去问客户，客户会给一个他自己算的数，那个数和图里的数迟早对不上。

路由错了后果各不相同，但都严重。把 ASK 当 WRITE 就是编造——最危险，因为成品最通顺。把 SEARCH 当 ASK 会耗尽客户的回答耐心，真正只有他能答的那几问反而被敷衍。

**SEARCH 与 COMPUTE 有一处关键差别：算出来的可以直接用，查回来的不行。** 检索结果必须先过适配性评估、排序，交客户勾选，选中的才入图。

判定程序、WRITE 的边界（agent 能生成什么、不能生成什么）、按槽位族的路由表、五种边界情形，全部在 `references/provenance-routing.yaml`。

## 素材摄入：客户交来一堆材料之后

真实工作形态是客户丢过来设计方案、造价书、批复、台账，说"照这些写"。材料永远不齐，缺的那部分若被顺手编出来，报告读起来最通顺，却在评审环节爆掉——而且编造的痕迹已被抹平，没人能倒查是哪一步开始虚构的。

所以动笔之前先把缺口摊开：

```bash
python3 scripts/intake_scan.py project.yaml
```

它输出四样东西：已登记素材台账、缺哪几类素材（含**追料话术**、找谁要、不给的后果、可接受的替代物）、哪些取值指不回具体材料的具体页、以及剩余缺口按上面的路由分派到 ASK / SEARCH / COMPUTE / WITHHOLD。

追料话术里要写**可接受的替代物**。"请提供投资估算书"客户可能没有；"投资估算书；若尚未编制，请提供概算指标表或立项批复中的投资规模，我们据此标为待细化"——后者能拿到东西。

素材分类（M1 批复 / M2 规划用地 / M3 设计 / M4 造价财务 / M5 施工 / M6 基础资料 / M7 专项评估 / M8 规范）、抽取契约、素材间冲突与版本的处置，见 `references/materials.yaml`。垂类在 `references/verticals/<id>/materials.yaml` 里规定本类必须的素材与追料话术。

**追料要有时限。** 没有时限的等待会一直等下去——直到某个人受不了了，随手把那个数填上。编造多数是这样发生的，不是恶意，是拖久了。

时钟从 `asked_at` 起算，按工作日走，分三档：催办 → 升级 → 决策。三档的天数按素材来源分（客户内部资料快、第三方委托成果慢、行政批复最慢且不由任何人控制）。**客户答复「正在办理中」不重置时钟**——那是最常见的规避方式，答一句就能无限延期的话，时限等于没有。

到决策点时停止等待，把四条出口摆给客户请其书面选一条：

| 出口 | 做法 | 代价 |
|---|---|---|
| **S1** 用可接受的替代物 | 概算指标顶正式估算等 | 证据等级下降，须在正文显式标注降级 |
| **S2** 显式留白 + 进 CH9 风险 | 列为前置条件未闭合，给办理计划 | 行政批复类的默认出口；可研本就允许手续办理中编制 |
| **S3** 缩小出具范围 | 该维度声明资料不足、本次不出结论 | 报告完整性下降，须客户书面确认 |
| **S4** 暂停并告知阻塞 | 停止推进，说清卡在哪 | 主干素材缺位时的唯一出口。暂停不是失败，带着空洞往下写、两周后返工才是 |

**到期不改变编造的性质，只是给了它一个借口。** 估一个、套同类、写"暂按经验值"，都不在出口之列。

到期必须**主动**告知，不能等客户来问。可研拖期的常见剧情是：agent 一直在等，客户以为在写，两周后才发现谁都没动——那时留给决策的时间已经没有了。

细则见 `references/materials.yaml → intake_sla`。

**收到什么程度算够？分三级，每级解锁一批动作。** 答"全部齐了"等于永远开不了工。L1 起步级只要五个回答、不需要任何素材，就能做骨架并过 G1——很多项目卡在"等资料"其实没必要，客户看见目录反而更清楚该给什么。L2 主干级要设计面积分项、造价构成、分类人数与存量，够了就能起草主干章节。L3 完备级要批复、用地、进度、专项评估，才能出稿送审。每轮扫描都报当前在哪一级、距下一级还差什么。

**篇幅要求也是一项收料内容，而且要问到分章。** 只问"总共多少页"不够——真正要问的是**哪几章评审看得最细**。这一问的价值不在字数，在重心：缺额法项目的规模论证章被一句话带过就是评审的靶子，而无关紧要的章写了三页会让读者觉得报告没有主次。和审批口惯例一样，这是只有做过的人才知道的信息，agent 查不到。

**篇幅要问三件事，缺一件都会在交付时出问题：总量、分章、口径。** 只问总量不问分章，各章配比会失衡——总量正好而结论章写成需求论证章的四倍，读者一眼看得出没有主次。只问分章不问总量，会出现另一种塌陷：分章下限设 90%，逐章都擦着线过，全篇就只有 90%，5 万字的要求变成 4.5 万，而客户是按总量提的要求。所以总量必须单独设一道门禁，且比分章更严。

**口径这一问最容易被跳过，也最容易出事。**「5 万字」至少有三种数法：不计空格字符数（Word 的口径，也是本 skill 语料库入库的口径）、纯汉字数（剔除标点、数字与拉丁字母）、折算字数。可研数字密集，前两者能差 15% 到 18%——同一份稿子，按第一种口径 5.1 万，按第二种就是 4.3 万。三处口径必须统一：语料库入库、篇幅门禁、交付前自查。不统一时最典型的事故是我们算达标、客户用 Word 一数不达标。客户说不清口径的，默认按不计空格字符数，并在交付说明中写明用的是哪一种。

**客户答不上分章字数时，默认目标取同垂类语料库的实测配比，而不是大纲权重。** 大纲权重是全垂类通用的粗权重；语料库配比是这一垂类里真实报告各章实际写了多少字，贴切得多。`length_gate.py --corpus <语料条目目录>` 会读 `index.yaml` 里的逐章字数换算成目标。配比只取字数与占比，不取任何值——与语料库其他用法同一条边界。

**客户给了分章字数就按客户的，写进 `project.yaml` 的 `sections[].length_target`，它优先于权重折算值**——那是输入，不是我们算出来的建议。没给的章退到「总预算 × 归一权重」；垂类模版里每章带的是权重，不是字数。

字数是**门禁**，不是提示：

```bash
python3 scripts/length_gate.py project.yaml content.yaml   # 未达标退出码 1
```

低于目标 90% 的章不放行。但门禁只解决"不放行"，不解决"怎么补"——**差 800 字时正确的动作不是「再写点」，是把图上还没写进这一章的东西找出来**。所以它的主要产出是缺口清单：本章还有哪些节点没写进正文、哪些必写项没核销、哪些检索没做、哪些取值点空着，每条附字数估算（估算常数从一份 5.4 万字的真实报告量得：定量陈述段均 83 字、依据引述 53 字）。

合法出口只有三条：**补事实**（清单里"已有值但正文没引用的节点"排最前，那些不需要再问任何人）、**补论证**、**请客户书面下调本章目标**。清单全部补完仍然不够，就是目标定高了，走第三条。抄规范条文充数、把一句话拆成三句、贴台账都不在出口之列——评审一眼看得出，而且会连带怀疑其余各章。只对正文计数，表格与插图不计，否则贴一张大表就能蒙混过关。偏长的先移附件，不删内容。规则见 `references/outline-shaping.yaml → length_budget`。

**排版格式同样要问，而且要在动笔前问。** 一份内容正确但排版不合规的可研，会在**收件环节**就被退回补正——收件的人不看内容看格式，这是最不值得丢的分。有明文的部分（公文格式国标、部分省市的报审文本要求）可以检索，但具体审批口的习惯查不到，只能问。问不到时的实用替代：请客户给一份该口近期通过的报告，照它的格式排——"请提供格式要求"客户多半没有，"给一份通过的报告"拿得到。

三套预设（报审文本 / 企业投资 / 紧凑版）见 `references/typography.yaml`，渲染时 `--preset` 切换。有一个实现层的坑写进了硬规则：**只设 `font.name` 只设了西文字体，中文会退回默认字体**，文档里中英文两种脸——而这个问题在装了对应字体的本机看不出来，发出去才被发现。所以必须同时设 `w:eastAsia`，渲染后还会打开成品复核一遍。页数超限时的顺序是**合并章节 → 移附件 → 才考虑压排版**：让评审读得累，不是省页数该付的代价。

**固定「要素清单」，不固定「文档模板」。** 甲方手上的材料形态千差万别——盖章 PDF、Excel 台账、微信里一段话都有。硬性要求"请按此模板填写"会显著降低回收率：填不进去的人干脆不填，本来能拿到的原始材料也拿不到。所以要素清单（要什么口径、什么粒度、缺了拿什么顶）必须固定，交材料的形式不固定。可以按要素清单导出一份 intake 表作**可选加速器**——它的价值不在收集，在**对齐口径**：客户填的时候会发现"原来要分全校/本期两个数"，这个发现本身就避免了后面的返工。但不得把"没按表格填"当成不推进的理由。

**收到哪一层才算收到：能复算的那一层，不是能填表的那一层。** 客户交来的「建安工程费 11188 万元」第一眼像源数据——它印在投资估算表上——实际是 27 个分项、四层汇总上来的；「科研人员 315 人」是四个研究中心的合计。把汇总值当源数据收，后果不是少了点细节，是**这条链从此不能重算**：改一个分项总数不跟着变，分项与合计对不上也查不出来（验过的真实报告里，室外总体工程分项之和 52 万元、合计写 49 万元，差 6.1%）。

判断方法是拿到一个数就问「它能不能由别的数算出来」——能就往下要一层。必须分项收的五类（投资估算明细、人员按组织单元×类别、配套用房间数与单间标准、用水量计算表、负荷计算表明细）见 `references/materials.yaml → granularity`。反过来也要认得出**哪些确实是源数据**：气象参数、既有财务决算、地勘结论；以及**规范限值表整张都不该建节点**——那是依据，不是本项目的事实。

**表格不是源数据的容器，是推演的一次呈现。** 所以正文与表格里都不许出现手打的数字，只能写 `{{节点名}}`，渲染时注入——`render.py` 会拦下手打的数并中止出稿。表的**行**也能由图谱生成（`rows_from` 按节点族），图上加一个配套用房分项，表自动多一行，不再依赖"记得去改"。

**两份素材给出同一节点的不同值时不许挑一个用。** 两个值都登记，标为素材冲突抛给客户裁决，裁决前依赖它的章节不起草。

## 外部证据：查回来不等于能用

一条管不着本项目的地方规定写进"政策符合性"，评审一眼看穿，整章的可信度一起塌。检索结果的处置是三步，不是一步：

```bash
python3 scripts/fit_rank.py project.yaml candidates.yaml
```

先硬否决（已废止 / 地域不覆盖 / 类别不覆盖 / 主体不适用），出局的**留痕备查**——评审问"为什么没引用某某文件"，这段留痕就是答案。再按六维打分排序：地域适配、类别适配、主体适配、时效、效力层级、条款针对性。最后呈一张勾选表，每条要说明为什么排在这个位置、采纳后挂到哪条边服务哪个维度、不采纳有什么后果。

**agent 不自行采纳任何一条。** 适配性的最终判断需要项目所在地的实务经验，而且采纳哪条政策会影响论证走向——那是客户的决定，不是工具的决定。C10 检查这一点。

检不到就说检不到，不许用一份"沾边"的文件顶上去。评分细则见 `references/external-fit.yaml`。

## 会过期的事实：软约束

图上的事实不是同一种东西，寿命差得很远。**硬约束**是这个项目的事实——面积、人数、投资、地点，它不会自己变，要变必须走客户确认 + 影响分析 + 留痕。**软约束**会随时间失效——规范版本、政策文号、面积定额、单方造价、统计数据、对标案例，它不因为写进了图就成立，只是"截至某日查到的是这个"。

这个区分以前是隐含的，代价很具体：软约束被当成硬约束保护起来，查到新版规范也不敢直接换，要走冲突裁决问客户"两个值用哪个"。客户看着 GB50189-2005 和 GB50189-2015 也不知道选哪个，事情就一直挂着，最后带着旧版本出稿。

**软约束被新证据替换不是冲突，不走裁决，直接换，但留痕。** 旧值不是"另一种意见"，是过期了。七类软约束各有保鲜期（规范版本 90 天最短，统计数据与对标值 365 天），过期不等于错，是"必须重新查一次才能用"。

三条边界：替换仍要过 `fit_rank.py` 的适配性评估——"更新"不等于"更适配"，一份新发的外省文件比不上一份在用的本省文件；定额与造价类替换后**必须重跑派生**（`impact.py`），只改定额不重算规模是图与正文脱节的标准入口；**建设单位的公开信息不接受检索单方替换**，查到的新信息仍须客户核对后才落图。

反过来也要守住：**硬约束的值变更，来源不得是 SEARCH**（C21c）。agent 查到一个"同类项目一般是多少"就去改客户的数，那不是更新，是编造，而且形式上看起来很像更新。

有一类容易判错——客户素材里的定额引用。指标本身是软的，但"客户认可按这个指标算"是硬的。查到指标换版了，要回去问客户"新版是 15 ㎡/生，是否按新版重算"，不是自己换了算。

分类、保鲜期、替换协议与检查 C21/C21b/C21c 见 `references/volatility.yaml`。各专业该引哪些规范见 `references/norms.yaml → design_basis_by_discipline`：那份清单从一份真实报告的各专业「设计依据」节反推而来（60 条），但只记 `code_seen`——"样本里写的是这个"，不是"应该引这个"。源样本自己就在这上面翻了车：同一份报告暖通章引 GB50189-2015、节能章引 GB50189-2005，《建筑照明设计标准》一处 2013 一处 2004，《无障碍设计规范》挂了两个编号。

## 建设内容怎么写实：子类 → 取值点 → 论证需求

「建设内容」章是评审看得最细、也最容易被指出"套模板"的一章。症状很典型：通风写"设置机械通风系统"、供电写"按二级负荷设计"——每一句都对，每一句都没说本项目。

**根因不是行文能力，是没问到取值点。** 评审追问的从来不是"有没有通风系统"，而是"换气次数取几次、通风柜几台、排风量多少"。所以这一章的自适应能力不来自更好的提示词——提示词写得再花，问不到 12 次/小时这个数，写出来的还是通用条款。

做法是把可变的部分收敛成**结构化的取值点**，按子类激活：

```bash
python3 scripts/claim_derive.py project.yaml
```

它做三件事：识别子类（可多选，一栋楼同时是湿实验室和洁净区是常态，取并集）→ 激活该子类的专业取值点（通用取值点 + 子类增量，按专业分组，每条说明问什么、为什么要问到数字、缺了哪一章会写成通用条款）→ 推出论证需求（适用维度 × 项目属性 × 子类 ⇒ 论点清单，每条论点按九种论据模式展开，每个缺失的论据槽标注该 ASK 还是 SEARCH）。

**论证需求也是推出来的，不由垂类写死。** 垂类手写会有两个必然结果：写不全（子类是长尾的，穷举不了），会过时（政策变了几十个垂类要一起改）。

三条硬规则：

- **识别不出子类时不许退回通用条款。** 正确处置是把全部子类的取值点取并集，反过来问客户"本项目是否涉及以下条件"。客户答"都不涉及"也是有效输入——它把通用条款从偷懒的默认变成有依据的选择，评审看得出这个区别。
- **允许写通用条款的专业必须在子类里显式列出**（`generic_clause_ok`）。不列 = 不允许。通用条款本身不是错，错的是在本项目有特殊性的专业上写通用条款。
- **取值点全部落地之前不要起草建设内容章**，写出来也是通用条款（C12）。

新增子类只加一段 YAML，不需要改任何代码。契约见 `references/discipline-probes.yaml → subtype_contract`，推演规则见 `references/claim-derivation.yaml`，子类定义在 `references/verticals/<id>/subtypes.yaml`。

## 章节内容项也会触发检索

前面说的 SEARCH 都是**由缺口触发**的：某个节点空着、某条规范没查证、某条论据缺支撑，于是去查。但可研里有一大类内容**不产生任何空节点，照样必须去查**：

「项目单位概况」要写单位沿革、业务规模、**科研工作及学术交流**、既往同类项目经验；「项目建设背景」要写行业发展现状；「要素保障分析」要写当地水电气热的供给条件。

这些不是数字，图上看不出任何缺口——**缺口分诊看不见它们**。结果就是这几章被写成场面话，而它们恰恰是评审判断「这份报告是不是认真做的」的第一印象来源。

所以内容项到检索任务的映射单独登记，并把分诊变量当**检索分面**注入：

```bash
python3 scripts/intake_gen.py project.yaml    # 客户提问 + 检索任务，一并输出
```

三条硬规则：

- **涉及本单位的检索必须带单位全称。** 不带单位名去查「科研工作及学术交流」，查回来的是行业综述，写进单位概况就是套话。缺单位全称时该任务被挡住并转 ASK，不硬查。
- **涉客户信息先核对后落笔。** 写进单位概况的每一句都是**以客户的名义在说**。同名单位、信息过时、官网的宣传口径——三个坑都在这里。
- **查不到不许用形容词补。** 「该单位科研实力雄厚、学术交流活跃」等于什么都没说，评审一眼看出是凑的，而且会连带怀疑其余各章。要写的是可核的具体项：几个国家级平台、近三年几项国家级课题、承办过哪几个学术会议。查不到就少写。

还有一条约束背景章的：**凡不能连到「所以本项目要建」的段落都该删**——背景是给必要性铺路的，不是行业综述。

任务目录见 `references/section-research.yaml`。它管「该去查什么」，`external-fit.yaml` 管「查回来的能不能用」，两者串联。

## 可研阶段的设计：agent 做到哪一步

可研里的「设计」是**方案深度**——说清楚采用什么方案、依据什么规范、关键取值是多少，而不是画出怎么建。这个深度里 agent 能承担的比直觉上多，所以每个专业取值点都带 `resolution`，分四层：

| 层 | 谁做 | 例子 |
|---|---|---|
| **规范判定** | agent 做，**必须带条款依据** | 建筑分类与耐火等级、抗震设防类别、防火分区上限、用水定额、用电指标 |
| **参数推导** | agent 算，不许手填 | 计算负荷与变压器容量、冷热负荷、最高日用水量、消防水池容积、人防配建面积 |
| **方案比选** | agent 给候选与比选要点，**客户或设计单位定** | 结构形式、空调形式与冷热源、装配率与绿建目标 |
| **设计单位专属** | agent 推不出来，只能要 | 柱网与构件尺寸、平面布置、管线综合、实验室换气次数与防振等级 |

把这四层混成一句「去问客户」会有两个后果：该自己算的推给了客户（客户嫌烦，真正只有他能答的反被敷衍），该设计单位定的被 agent 编了（最危险）。推导模板见 `derivations.yaml` 的 T18–T23。

判断一段技术方案够不够可研深度，问三句：**采用什么方案**（有明确结论，不是"根据需要设置"）、**依据什么**（规范条款 / 客户确认 / 设计单位提供，三者选一）、**关键取值是多少**（有数字，不是"满足规范要求"）。三句都答得上就够了，不必等施工图。

## 每章一套起草提示

用一套通用提示词写十几章，出来的必然是同一种腔调的流水账。**每一章其实是不同的活**：必要性章在论证（最容易断链）、规模章在测算（要能被逐条复核）、技术方案章在判定与取值（最容易写成通用条款）、投资章在归集（费用构成必须闭合）、结论章在复述（一个新数都不许出现）。

```bash
python3 scripts/claim_derive.py project.yaml --prompt technical
```

每章的提示绑定到它的切片：服务哪个维度、用哪些节点、**起草前必须先完成什么**、必须写到什么、这一章特有的坑是什么、评审盯什么、篇幅重心在哪。

`prepare` 是硬门禁：没做完就不要动笔。「先写起来再说」是返工的主要来源——前置没做完写出来的段落，客户读到的是通顺的文字，会去改句子而不是补事实。

见 `references/section-prompts.yaml`。垂类可在 `outline.yaml` 的章节上加 `prompt_extra` 追加本垂类要点——追加，不替换。

## 参照同类报告：借形不借值

做过的报告攒成库、写新报告时按章参照，能补上图谱补不了的东西：该审批口认可的话术、章节的详略与铺陈、表格的栏目设置、纯定性内容的行业写法。

但检索到的历史章节里混着两种东西——可复用的**形**和不可复用的**值**，而它们在文本里长得一模一样。参照写作最常见的错误不是没参照，是**参照得太完整**：上一份的面积、单方造价、政策文号顺手带进了新报告，带进来之后正文读起来毫无异常。所以入库时**强制脱值**，数字、专名、地名、文号、规范编号全部替换成槽位标记。提醒「注意不要照抄数字」不管用；把值物理抽掉，就带不过来。

```bash
python3 scripts/corpus.py ingest 历史报告.docx --graph 该报告的图.yaml --meta meta.yaml -o corpus/<id>
python3 scripts/corpus.py retrieve corpus/ --section technical --vertical edu-research
```

三者分工不重叠：**语料库管形，图谱管值，法定大纲管覆盖**。

**存储、检索、写作、图谱锚定用同一个粒度：语义 chunk。** 一个 chunk 一个 MD，外加一份 `index.yaml`。chunk 的边界取「写作单元」——一次可交付的写作、一次可核对的事实闭合。实测一份 5.4 万字的高校科研用房可研切出 71 个 chunk，设计方案章 7 个（设计总说明 / 建筑 / 结构 / 给排水 / 强电 / 弱电 / 暖通）。chunk_id 用 `章节key-序号`（`technical-03`），不用内容哈希——哈希会在改一个错别字之后变，图上挂着的引用不该因此断掉。正文落 MD 不落 YAML，是因为入库会报回一批疑似漏投影的专名（实测 29 个）必须有人过一遍，40 万字塞进一个 YAML 没人读得动；拆开之后检索只读索引，**物理上不可能顺手把原文带进起草上下文**。

`retrieve` 的产物是**一段提示词，不是一段可续写的文本**。历史章节在这一步已经被量成了段落功能顺序、篇幅分布、表格栏目、收尾方式，原文不进起草上下文——原文一旦进来，模型就不再是「写」而是「改」，产出必然带着那份报告的骨相，脱不脱值都一样。要看原文得显式加 `--show-skeleton`，那是给人核对用的。

库里的规范编号、政策文号一律按**软约束**处理，而且默认已过期——库里那份报告是哪年编的，编号就是哪年的。检索到的 chunk 提示「这里要引一条节能设计标准」，具体引哪一版现查，查到的新版直接替换（见下一节）。

**历史库不是正确性的来源。** 验过的两份真实报告，一份缺 8 章法定内容、一份缺 6 章，还各有断链论证与错引规范名称。所以入库时跑一遍检查器把缺陷标在库里，检索时一并返回——参照一份缺 warrant 的必要性章，写出来的多半也缺 warrant。旧口径条目（`outline_version` 早于现行大纲）**只参照行文，不参照结构**。

入库最脆的一环是切章，可靠性完全取决于源文档有没有标题样式；没有样式的（.doc 转换件常见）只能靠编号与长度启发式，脚本会如实报告用的是哪种锚点。边界 P1–P6 与检查 C19a/b/c 见 `references/corpus.yaml`。

## 工作方式：状态机，不是流水线

**不要一次写完整篇再请客户通篇修改。** 那样做，一个上游事实变动会导致下游全面返工，而且成品外观会降低客户的审阅强度。

正确形态是循环：

```
评估图状态 → 选一个动作 → 执行 → 回写图 → 重跑检查 → 再评估
```

每轮只推进一小步，每一步可回退。动作有五种，按优先级选：

| 优先级 | 条件 | 动作 |
|---|---|---|
| 1 | 有 error 级冲突 | **RESOLVE** 消解冲突（绝不带着冲突往下走） |
| 2 | 有高阻塞度空槽，缺 E1/E6 证据 | **ASK** 问客户 |
| 2 | 有高阻塞度空槽，缺 E2/E3 证据 | **SEARCH** 查外部（不占客户时间，尽量批量前置；结果须经 `fit_rank.py` 排序后交客户勾选） |
| 3 | 某规则输入已齐 | **COMPUTE** 算（自动，不打扰） |
| 4 | 某章 requires 已闭合且论证完备 | **DRAFT** 起草该章 |

提问时按**阻塞度降序**，不按章节顺序。先问总建筑面积（阻塞造价、负荷、能耗、进度四条链），再问装修标准（只阻塞造价一条链）。每批不超过 5 个问题，并说明这个问题服务于哪个可行性维度、不答会卡住哪几章。

细则见 `references/interaction.yaml`。

## 四道闸门

| 闸门 | 时机 | 拦住什么 |
|---|---|---|
| **G1 骨架确认** | 分诊完成后，一切内容工作之前 | 全部后续动作 |
| **G2 关键事实确认** | 高阻塞度节点取值确定时 | 依赖它的全部章节的起草 |
| **G3 逐章确认** | 每章起草完成时 | 该章 provides 节点的冻结 |
| **G4 出稿** | 全部章节完成 | C1–C7 未全绿或未留痕裁决 |

G1 之所以是硬闸门：章节 id 是全图的引用锚点，冻结后再改等于全图返工。

## 执行流程

### 第一步：分诊

先问清楚这几件事，其中**「由谁投资」无法从项目名称推断，必须客户明确**——它决定用哪本大纲、C7 查哪套覆盖、D11 盈利能力是否适用。

**「项目具体在哪个省哪个市」同样必须客户明确，不得从单位名称推断**——多校区、多厂区的单位，注册地与项目所在地经常不是一个地方。答错这一问会把一整套管不着本项目的地方规定固化进报告。

从项目名称可以初步推断建设性质、功能类型、主体类型，但推断结果一律须客户确认。

完整问题清单见 `references/triage.yaml`。分诊之后、动笔之前，先跑一遍 `intake_scan.py` 把素材缺口摊开。

### 第二步：生成骨架并请客户确认（G1）

三层解耦，这是骨架生成的核心逻辑：

| 层 | 管什么 | 可变性 |
|---|---|---|
| 法定大纲（`references/outline-*.yaml`） | 必须覆盖什么内容 | 不可裁剪 |
| 垂类章节模版（`references/verticals/*/outline.yaml`） | 分几章、怎么排、叫什么名 | 由垂类决定 |
| 本项目骨架 | 本项目实际目录 | 生成后经客户确认冻结 |

**标题可变，覆盖不可少。** 三者通过 `covers` 字段映射。这就是「神似形不似」的机检定义：**神 = covers 全集 + D1–D11 合取分解 + 数据链拓扑，形 = 章节数、排序、命名、详略。**

垂类模版若是一套写死的章节，报省里的和报部委的会长得一模一样，评审一眼看出是模板。所以骨架要按甲方基本情况**变形**——七个算子：合并 / 拆分 / 升级 / 降级 / 调序 / 追加子节 / 声明不适用。变形只搬动内容的容器，不增减内容本身，合法性只看一条：covers 全集是否不变（C7 守门）。

决定「形」的那组变量里，两个必须问客户、agent 查不到：**报给谁审**（报部委和报市里的形态差别很大，问不到就按最高层级从严——从严的可以删，从简的补不回来），和**该审批口的章节惯例**（成文规范里查不到，但不遵守会被退回补正）。

篇幅有上限时先合并容器，不删内容——**篇幅压力不构成删 covers 的理由**。算子、变形规则与不变量见 `references/outline-shaping.yaml`。

呈给客户的骨架表要有四列：章号 / 章节标题 / 承载的法定内容 / 状态。并单独列出判定为"不适用"的章节及理由，请客户逐条确认。

客户可以改标题、调顺序、增垂类子节、推翻"不适用"判定。客户**不能**删除任何法定 covers——遇到这种要求，说明这条来自哪本大纲哪一款、删了会在评审环节被打回，而不是简单拒绝。

### 第三步：图驱动循环

按上面的动作优先级循环推进。每次回写图后重跑检查。

起草某章之前确认三件事：该章 requires 的节点全部满足、该章服务的维度其论证已填满 Toulmin 必填项、图上无未解决的 error。不满足就不写。

三件事都满足了，起草这一章还差**查**和**借鉴**两步。一条命令合成：

```bash
python3 scripts/section_brief.py project.yaml --section technical --corpus corpus/
```

简报固定四节，顺序是硬的：① 本章图谱切片与起草前置 ② 这一章的法定内容项触发了哪些检索 ③ 同类报告这一章的**形** ④ 逐段写作计划。**先把事实定下来，再考虑怎么表述**——反过来做（先照着同类报告起个稿再往里填数）是套模板的标准路径。

第四节按写作单元排表：每个单元多少段、目标多少字、承载哪几条必写项。**一段一交**：写完一段就核，核完再写下一段。整章写完再核，返工的是整章，而且成稿的外观会让客户只改句子不补事实。段数不必等于历史样本——图谱里还有没写到的必写项就加段，历史有而本项目没有对应事实的就删段，**不许为了凑段数注水**。挂不到具体单元的必写项单独列出逐条核销，剩下的就是这一章漏写的法定内容。

**DRAFT 动作产出的是 `content.yaml` 里的章节条目，不是散落在对话里的文字。** 正文写进 `content.yaml`，数字写成 `{{节点名}}` 占位符，最后由 `render.py` 一次性渲染成 Word。照着 `templates/content-template.yaml` 的结构写。

在对话里直接输出正文而不落到 `content.yaml`，等于放弃了 SSOT——那些数字就再也不跟着图走了。

### 第四步：出稿（G4）

跑完整校验，然后**渲染出 Word 文档**，连同检查报告与审计包一起交付：

```bash
# ① 先校验。有 error 先解决，不要带着冲突渲染
python3 scripts/validators.py project.yaml --json check.json

# ② 渲染成 Word —— 这一步产出的 out/report.docx 才是交付物
python3 scripts/render.py project.yaml content.yaml -o out/

# ③ 篇幅门禁 —— 分章未达标或全篇总量未达标都不放行
python3 scripts/length_gate.py project.yaml content.yaml \
    --corpus corpus/<垂类>/<条目>/ --count-mode nows

# ④ 审计包
python3 scripts/audit.py trace project.yaml -o audit/
```

`render.py` 输出这些东西：`out/report.docx`（成品）、`out/bindings.json`（锚点绑定表，客户改稿后回读要用）、`out/snapshot.json`（本次渲染的图快照）；同时报出每章字数与篇幅偏离，以及 `out/figures/*.svg`（生成的示意图源文件）。中间两个不交给客户，但**必须留着**——没有 bindings.json，第五步的回读就退化成文本匹配。

用 `SendUserFile` 把 `report.docx` 交给客户。只贴一段正文或只给 `project.yaml` 都不算交付。

审计包含派生轨迹（每个数字用了哪条规则、上溯到哪些叶子输入、依据是什么）与防篡改指纹。可研要过评审、要备案，出了问题要能倒查——人写的报告只有结论没有过程，答不上来。

设 `FSR_AUDIT_KEY` 环境变量可启用 HMAC 签名；不设则退化为 SHA256，只能验完整性、不能证明来源。

每笔变更用 `audit.py log` 入账，链式哈希，改中间任何一条后面全部失配。

### 第五步：客户改稿后的回读

客户一定会直接改 Word 文档。如果不回读，那份稿子就脱离了图谱，此后所有一致性保证失效。

回读要分类处置：改客户给定事实 → 接受并传播；改派生值 → 拒绝并问清楚是哪个上游变了；只改了复述处 → 拒绝并指出权威来源在哪一章；改行文不改事实 → 接受，记入文风偏好；删内容 → 检查是否导致法定覆盖失守。

用 `scripts/reconcile.py` 执行。它支持两种模式：

- **协同文档**（推荐）：平台给稳定块 ID + 变更事件，定位是确定的，还能实时批注影响
- **docx 往返**：靠渲染时埋的书签定位，书签被破坏时退化为文本匹配，无主变更率更高

拒绝时要给足裁决信息。改派生值时，脚本会列出该值的公式与全部上游取值，并说明「您想说的多半不是『这个数变成 21000』，而是某个上游变了」。

完整机制见 `references/reconcile.yaml`。

`schema.py` 是被引用的模块，不单独调用。

**改任何上游事实之前先跑 `impact.py`。** 先给影响清单再执行——让客户看见这一笔修改的真实代价，而不是改完之后才发现要重写四章。它只报本次变更**新引入**的错误，不把既有问题混进来。

**schema 先于语义检查**：结构不合法时直接中止，不输出任何"通过"。在坏图上跑 C1–C7，产出的通过是误导性的——曾经把某个节点值写成字符串「一百」，检查器不报错、不计算、只输出一条通过项。那叫漏检，比误报危险。

### 渲染的硬约束

`content.yaml` 的正文**不许出现字面数字，只能写 `{{节点名}}`**。这不是风格要求，是物理保障：人一旦能直接把 26400 敲进正文，SSOT 就破了。遇到未声明的占位符，`render.py` 直接中止，不生成半成品——带着未解析占位符的稿子一旦流出，就会有人手工填数字。

模板见 `templates/content-template.yaml`。

### 插图：客户没给图时怎么办

可研里有两类图，性质完全不同，处置也相反。

**数据图可以生成。** 面积构成、投资构成、资金平衡、缺额对比、进度横道——它们的全部内容都来自图上已确认的节点，画图只是换一种表述方式，**不引入任何新事实**。正文里写 `{{figure:F_XXX}}`，渲染时生成 SVG 并嵌入该段落，同时把 SVG 落到 `out/figures/` 供排版单独取用。

**设计图一律不生成。** 总平面、建筑平面立面剖面、结构布置、机电系统、管线综合、效果图、工艺流程图——它们承载的是设计单位的专业判断：柱网怎么排、管线怎么走、疏散怎么组织。这些内容 agent 没有也推不出来。**画出来是最难被发现的一种编造**：一张看起来像模像样的平面图，评审会当成设计成果来审，审出来的问题却记到设计单位头上。缺设计图时正文写「详见设计单位提供的 XX 图」，并列入 M3 素材缺口。

判据是一句话：**这张图里有没有「图上没有的信息」。** 有就是设计图，不画。拿不准时按设计图处理。

生成图受四条约束：图上每个数字都必须来自节点（不许有只存在于图里的数）；所需节点缺任何一个直接中止，不出半成品；图题固定标「示意图，据本报告数据生成」，不得署设计单位名；图注列出所用节点，可倒查。构成类图还会核对分项之和是否等于合计——**「图漏了一个分项」由此从靠人看变成了可机检**。

客户后续提供正式图时用正式图替换，示意图退出，不并列。清单与规则见 `references/figures.yaml`。

### 检查项

`S1–S6` 结构层 · `C1–C7` 语义层 · `C8` 取值可溯源 · `C10` 外部依据须经适配性评估与客户确认 ·
`C11` 来源路由不得违反 · `C12` 专业取值点覆盖 · `C13` 论点覆盖 ·
`C14` 参照值须诚实标注 · `C15` 插图数据可溯源 · `C16` 排版规格已落地 · `C17` 章节检索任务覆盖 · `C18` 起草前置条件 · `C19a` 槽位已解析 · `C19b` 参照来源未泄漏 · `C19c` 缺陷清单已过目 · `C21` 软约束在保鲜期内 · `C21b` 软约束已标注 · `C21c` 硬约束未被检索替换 · `CYCLE` 派生回环。每条检查的权威定义在
`references/ontology-core.yaml → constraints`、`ontology-argumentation.yaml → constraints`、
`materials.yaml → constraints`、`external-fit.yaml → constraints`、`provenance-routing.yaml → constraints`；
检查器输出自带码号与说明，不必先背下来。

检查器只报告，不自动改。数字对不对由客户负责，图谱只负责数字在传播中不矛盾。

冲突要抛给客户裁决，但必须给足裁决信息：冲突在哪两处、各自值多少、图中权威值是什么、改哪边影响哪些下游。

## 论证结构

可研的核心是论证可行性。每条论断填一个 Toulmin 六元组：**论点 / 论据 / 保证 / 支撑 / 限定 / 反驳**。

写的时候特别注意「保证」这一项——它是最常被省略的一环。真实样本里，从"国家有大数据战略"到"本校必须建这栋楼"，中间那一步从头到尾没写出来。检查器会把它标为「断链论证」。

顶层论断按**合取**分解为可行性维度：任一适用维度不成立则整体不成立。维度是条件性的，不适用时必须显式声明理由，声明了才放行。

六元组各项的定义、维度 D1–D11 的清单与依赖关系、适用性判定规则，全部在
`references/ontology-argumentation.yaml`（grep `^    D[0-9]+:` 看维度，`^  [a-z]+:` 看六元组）。

## 证据

六级 E1–E6，定义与各自的必填项见 `references/ontology-argumentation.yaml → evidence_model`。
操作上只需记住分诊规则：

空槽自动分诊：缺 E1/E6 → 生成客户提问；缺 E2/E3 → 生成 web 检索任务。**每次成稿前必须重新核验 E2**，规范换版是可研被打回的高频原因。

E2 的登记与调度见 `references/norms.yaml`。它有一条纪律：**不臆断任何规范的现行状态**——查不到就标 `in_use_unverified` 并写明查过哪些渠道，绝不因为"业内都在用"就标成已查证。登记册的价值全部建立在它不撒谎之上。

它还能抓写法错误：真实样本把《普通高等学校建筑面积指标》写成《普通高等学校建筑**规划**面积指标》，编号对、名字错，评审会直接指出。

## 政策法规：一个节点，四种角色

一切政策、法规、标准、批复统一为 `Mandate` 节点，全图只存一份，绝不按章节重复录入。但角色不塌缩：

| 角色 | 边 | 服务 |
|---|---|---|
| driver 强制驱动 | `mandates` | D1 必要性——政策要求我们做这件事 |
| benchmark 合规基准 | `complies_with` | D2 合规性——我们做的不违反政策 |
| warrant 推理保证 | `warrants` | 任意论断的推理许可 |
| domain 取值域约束 | `constrains` | 技术方案取值边界 |

同一份规划纲要，在必要性章是驱动，在合规性小节是基准。把这两条边混为一谈，是可研里极常见的论证含混。

「政策法规符合性对照表」不是手写的表，是 `complies_with` 边全集的渲染结果。D2 的论证模板 L0 已内置（`AU_COMPLIANCE`），垂类不用写。

## 本垂类

| 垂类 | 高校科研用房 |
|---|---|
| 法定大纲 | `references/outline-gov-2023.yaml`（政府投资通用大纲，强制适用） |
| 验证状态 | **规则集已在真实报告上验算闭合**：规模链/造价链/资金链逐条复现，检查器命中的缺陷经人工确认（记录留在 base，不随本包交付） |
| 规模论证 | **纯指标法**：分类人数 × 人均建筑面积指标。通常不做缺额法 |
| 必要性落点 | 学科发展与科研平台的空间需求，不是"人多了要地方坐" |
| 特有关注 | 实验室专项设计、拆除重建的四件事、实验室仪器设备费是否计入 |

加载 `references/vertical/` 下的 `profile.yaml`（领域槽位与词表）、`outline.yaml`（章节模版）、

**分诊时必问两件事**，它们决定整个测算：

① **规划人数必须分类给出**——科研人员与研究生的人均指标不同，只给总数无法测算。
② **实验室仪器设备费是否计入总投资**——各校口径不同，金额巨大，漏问会让投资估算整体失真。

## 交付前自查

出稿前逐条过一遍，任何一条不满足就还不能交：

1. `out/report.docx` 已生成，能正常打开，目录与章号连续
2. 文中没有残留的 `{{占位符}}`——`render.py` 遇到未声明的占位符会中止，正常出文件即说明这条已过
3. `validators.py` 全绿，或未绿项已留痕裁决
4. `is_placeholder: true` 的参照值已逐条处置（替换成实定值，或客户确认按参照值出稿）
5. 追料到期项已有客户书面选定的出口（S1–S4）
6. 已用 `SendUserFile` 把 docx 交给客户，不是只贴一段文字
