## 脚本

十四个脚本，全部已通过 `scripts/run_tests.py`（638 项断言）。

| 脚本 | 用途 |
|---|---|
| `scripts/validators.py <project.yaml>` | schema 校验 + C1–C7 一致性检查。退出码 0=通过 1=有错 2=结构崩坏 |
| `scripts/intake_scan.py <project.yaml>` | 素材摄入扫描：缺哪类素材、追料话术、取值可溯源、缺口按来源路由分派 |
| `scripts/claim_derive.py <project.yaml> [--prompt <章>]` | 子类识别 + 取值点按 resolution 分层 + 论证推演 + 逐章起草提示 |
| `scripts/fit_rank.py <project.yaml> <candidates.yaml>` | 外部证据硬否决 + 六维打分排序，出一张给客户勾选的表 |
| `scripts/intake_gen.py <project.yaml> --batch 5` | 客户提问（按阻塞度排序）+ 章节内容项触发的检索任务 |
| `scripts/impact.py <project.yaml> --set 节点=值` | 变更影响分析：算出会牵动哪些派生值、哪些章节要重写 |
| `scripts/figures.py <project.yaml> <F_ID>` | 单张插图调试。生成受 `figures.yaml` 约束，设计图一律拒绝 |

| `scripts/section_brief.py <project.yaml> --section <章> [--corpus corpus/]` | 逐章简报：图谱切片 + 本章检索任务 + 同类报告的形 + 逐段写作计划 |
| `scripts/length_gate.py <project.yaml> <content.yaml> [--corpus DIR] [--count-mode nows\|han\|cjk]` | 篇幅门禁：**分章 + 全篇总量**双判定，附缺口清单（缺哪些节点/必写项/检索/取值点）与配比偏离提示；默认目标取语料库实测配比 |
| `scripts/render.py <project.yaml> <content.yaml> -o out/ [--pages N] [--preset ...]` | **产出最终交付物** `out/report.docx`，附 bindings.json 与快照 |

| `scripts/audit.py trace\|log\|verify` | 审计留痕：派生轨迹、变更日志、防篡改指纹 |
| `scripts/run_tests.py` | 测试套件。改动脚本或本体资产后跑一遍 |

`schema.py` 是被引用的模块，不单独调用。

**改任何上游事实之前先跑 `impact.py`。** 先给影响清单再执行——让客户看见这一笔修改的真实代价，而不是改完之后才发现要重写四章。它只报本次变更**新引入**的错误，不把既有问题混进来。

**schema 先于语义检查**：结构不合法时直接中止，不输出任何"通过"。在坏图上跑 C1–C7，产出的通过是误导性的——曾经把某个节点值写成字符串「一百」，检查器不报错、不计算、只输出一条通过项。那叫漏检，比误报危险。

### 渲染的硬约束

`content.yaml` 的正文**不许出现字面数字，只能写 `{{节点名}}`**。这不是风格要求，是物理保障：人一旦能直接把 26400 敲进正文，SSOT 就破了。遇到未声明的占位符，`render.py` 直接中止，不生成半成品——带着未解析占位符的稿子一旦流出，就会有人手工填数字。

模板见 `templates/content-template.yaml`。

### 插图：客户没给图时怎么办

可研里有两类图，性质完全不同，处置也相反。

**数据图可以生成。** 面积构成、投资构成、资金平衡、缺额对比、进度横道——它们的全部内容都来自图上已确认的节点，画图只是换一种表述方式，**不引入任何新事实**。正文里写 `{{figure:F_XXX}}`，渲染时生成 SVG 并嵌入该段落，同时把 SVG 落到 `out/figures/` 供排版单独取用。

**设计图一律不生成。** 总平面、建筑平面立面剖面、结构布置、机电系统、管线综合、效果图、工艺流程图——它们承载的是设计单位的专业判断：柱网怎么排、管线怎么走、疏散怎么组织。这些内容 agent 没有也推不出来。**画出来是最难被发现的一种编造**：一张看起来像模像样的平面图，评审会当成设计成果来审，审出来的问题却记到设计单位头上。缺设计图时正文写「详见设计单位提供的 XX 图」，并列入 M3 素材缺口。

判据是一句话：**这张图里有没有「图上没有的信息」。** 有就是设计图，不画。拿不准时按设计图处理。

生成图受四条约束：图上每个数字都必须来自节点（不许有只存在于图里的数）；所需节点缺任何一个直接中止，不出半成品；图题固定标「示意图，据本报告数据生成」，不得署设计单位名；图注列出所用节点，可倒查。构成类图还会核对分项之和是否等于合计——**「图漏了一个分项」由此从靠人看变成了可机检**。

客户后续提供正式图时用正式图替换，示意图退出，不并列。清单与规则见 `references/figures.yaml`。

### 检查项

`S1–S6` 结构层 · `C1–C7` 语义层 · `C8` 取值可溯源 · `C10` 外部依据须经适配性评估与客户确认 ·
`C11` 来源路由不得违反 · `C12` 专业取值点覆盖 · `C13` 论点覆盖 ·
`C14` 参照值须诚实标注 · `C15` 插图数据可溯源 · `C16` 排版规格已落地 · `C17` 章节检索任务覆盖 · `C18` 起草前置条件 · `C19a` 槽位已解析 · `C19b` 参照来源未泄漏 · `C19c` 缺陷清单已过目 · `C21` 软约束在保鲜期内 · `C21b` 软约束已标注 · `C21c` 硬约束未被检索替换 · `CYCLE` 派生回环。每条检查的权威定义在
`references/ontology-core.yaml → constraints`、`ontology-argumentation.yaml → constraints`、
`materials.yaml → constraints`、`external-fit.yaml → constraints`、`provenance-routing.yaml → constraints`；
检查器输出自带码号与说明，不必先背下来。

检查器只报告，不自动改。数字对不对由客户负责，图谱只负责数字在传播中不矛盾。

冲突要抛给客户裁决，但必须给足裁决信息：冲突在哪两处、各自值多少、图中权威值是什么、改哪边影响哪些下游。
